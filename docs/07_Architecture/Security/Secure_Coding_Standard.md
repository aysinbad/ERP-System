> **Scope & authority.** This is the authoritative **secure coding standard** for the ERP repository. It defines *how code must be written and reviewed*; it derives from — and never overrides — the Security Architecture, the Threat Model, the Posting Service Spec, `AGENTS.md`, and `DEVELOPMENT_RULES.md`. It contains **no application code** and creates **no new business requirements**. Where it references a control, that control is a **mandatory standard for future implementation**, not a claim that the control is already built.
>
> **Control-status honesty (inherited).** The only running system today is the prototype, which carries real weaknesses (KI-001/002/003/004 and related, all **open**). The controls named here are **Designed/Planned, not built**. Nothing in this document closes a Known Issue, and **no claim is made that the system is secure** — no absolute-security claim is permitted anywhere in the repository.
>
> **Normative language.** `MUST` / `MUST NOT` are mandatory and objectively reviewable or testable. `SHOULD` is a strong recommendation requiring justification to deviate. `MAY` is permitted. Every `MUST`/`MUST NOT` in this document carries a rule ID (`R-§.n`) for traceability and review sign-off.

## 1. Scope and Authority

This standard applies to **all code and configuration** in the ERP repository, whether written by a human or generated by an AI tool. In scope:

- Backend APIs and HTTP handlers.
- Domain and application services.
- Database code, stored logic, and migrations.
- Frontend (web) code.
- Background workers and scheduled jobs.
- File processing and document generation.
- Email ingestion.
- External integrations (payment, tax, e-invoice, shipping).
- Infrastructure and hosting configuration.
- Automated and AI-generated code.

**Rules**

- **R-1.1 — MUST** apply this standard to every artefact listed above without exception.
- **R-1.2 — MUST** treat AI-generated code as subject to the **same** architecture, security, review, and testing rules as human-written code.
- **R-1.3 — MUST NOT** allow any AI-generated code to bypass architecture, security, testing, or approval gates (gates G1–G5, Security Architecture §16).
- **R-1.4 — MUST** resolve conflicts in favour of the higher source of truth: Accepted ADRs + approved Business Logic + Glossary, then the Prototype (ADR-000) for undocumented behaviour, then Known Issues as *required corrections* (`DEVELOPMENT_RULES.md` §2; `AGENTS.md`). This document never overrides those.
- **R-1.5 — MUST** apply ASVS 5.0 Level 2 as the minimum baseline platform-wide, and the selected Level 3 controls to the high-risk domains named by the Security Architecture: Accounting, Payments, User Administration, Security Administration, Period Lock, Posting Rules, Audit, Export Documents, File Management.

## 2. Secure Development Principles

These operationalise Security Architecture §1–§3 in code.

- **R-2.1 Deny by default — MUST** make the safe outcome the default; every access, endpoint, permission, file, and worker denies until explicitly granted.
- **R-2.2 Least privilege — MUST** give every identity (user, service, DB principal, worker) the minimum rights required and no ambient admin rights.
- **R-2.3 Fail securely — MUST** deny and preserve integrity on any error or uncertainty; a failed authorization, validation, lock, audit, or Outbox write **MUST** reject or roll back the operation, never proceed.
- **R-2.4 Defence in depth — MUST NOT** rely on a single control (e.g. UI hiding) as the only barrier; server, database, and audit layers each enforce independently.
- **R-2.5 Explicit trust boundaries — MUST** treat all upstream input (browser, worker, internal service, file, email, integration) as untrusted and re-validate at each boundary (Security Architecture §3).
- **R-2.6 Server-side enforcement — MUST** make every security decision on the server; client state is never authoritative.
- **R-2.7 Immutable accounting records — MUST** keep posted legal-ledger records append-only; correction is by reversal only (Posting Spec AI-3/AI-4/AI-5).
- **R-2.8 Tenant isolation — MUST** scope every data operation to the authenticated principal's `CompanyId` (and branch where applicable), resolved server-side.
- **R-2.9 Secure defaults — MUST** ship the locked-down configuration by default; relaxation is explicit, justified, and audited (Security Architecture §2).
- **R-2.10 No security through obscurity — MUST NOT** treat obscurity (hidden endpoints, non-obvious identifiers, encoding) as a control.
- **R-2.11 No absolute-security claim — MUST NOT** state or imply in code, comments, docs, or artefacts that the system is secure, unbreakable, or fully protected.

## 3. Input Validation

Implements Security Architecture §8 (validation, allow-lists, payload limits) and SEC-AC-13/14; mitigates T-08/T-26.

- **R-3.1 — MUST** bind requests to explicit DTOs with an **allow-list** of accepted fields; unknown or unexpected fields **MUST** be rejected (no open binding).
- **R-3.2 — MUST** validate type, length, range, format, and **semantic** correctness of every field server-side before use.
- **R-3.3 — MUST** canonicalise input (encoding, Unicode, path, case) **before** validation, and validate the canonical form.
- **R-3.4 — MUST** resolve tenant identifiers (`CompanyId`, `BranchId`) from the trusted identity context, never from the request body, query, header, or cookie.
- **R-3.5 — MUST NOT** accept from the client any `CompanyId`, `BranchId`, role, permission, account line, posting line, price/cost line, or other security or financial decision. The server derives these.
- **R-3.6 — MUST** enforce request and per-field **payload size limits**; oversized requests are rejected before processing (413/typed error).
- **R-3.7 — MUST** parse dates, decimals, currency, and identifiers with explicit, culture-invariant, precision-safe handling (money `DECIMAL(19,4)`, FX `DECIMAL(19,8)`, banker's rounding at storage — Posting Spec §12); no implicit locale parsing.
- **R-3.8 — MUST** validate dynamic/semi-structured payloads against an explicit **JSON schema**; no free-form untyped blobs are accepted as trusted input.
- **R-3.9 — MUST** validate uploaded file content by **magic bytes** (content inspection), not by the declared extension or MIME header alone (see §12).
- **R-3.10 — MUST NOT** use a deny-list as the primary validation control; allow-lists are primary (Security Architecture §8).

**Prohibited (non-compliant)**
```
// Binds every posted field, including CompanyId / IsAdmin — mass assignment.
var entity = await BindAllAsync(Request.Body);

// Trusts the client to say which tenant it is.
var companyId = request.CompanyId;
```

**Compliant (illustrative, non-authoritative)**
```
// Explicit DTO with allow-listed fields only; unknown fields rejected by config.
public sealed record CreateProformaDto(string CustomerRef, IReadOnlyList<LineDto> Lines);

// Tenant comes from the authenticated principal, never the payload.
var companyId = principal.CompanyId;   // server-resolved
```

## 4. Output Encoding and Frontend Security

Mitigates DOM/reflected/stored XSS and open-redirect classes; complements Security Architecture §8 HTTP headers (CSP, nosniff, frame-ancestors).

- **R-4.1 — MUST** apply **contextual** encoding (HTML body, attribute, URL, JavaScript, CSS) appropriate to each output sink.
- **R-4.2 — MUST** rely on framework-native, auto-escaping rendering for user-influenced content.
- **R-4.3 — MUST NOT** inject raw/unescaped HTML from user-influenced data (no `dangerouslySetInnerHTML`, `innerHTML`, `v-html`, `Html.Raw`, or equivalent) without a vetted sanitiser and documented justification.
- **R-4.4 — MUST** keep code compatible with a default-deny **Content-Security-Policy**; no inline scripts/handlers where avoidable, no `eval`, no dynamic script construction from input.
- **R-4.5 — MUST** prevent DOM XSS by avoiding sink assignment from untrusted sources (`location`, `document.write`, template injection); use safe DOM APIs.
- **R-4.6 — MUST** treat all user-generated text as data on render — never as markup or executable content.
- **R-4.7 — MUST** generate safe, sanitised **download filenames** (no path separators, control characters, or executable double-extensions).
- **R-4.8 — MUST NOT** redirect to a URL derived from untrusted input unless the target is validated against an allow-list (open-redirect prevention).

## 5. Authentication and Session Coding

Implements Security Architecture §4; mitigates T-01/T-02/T-03; SEC-AC-01/03/04/05. **Implements the designed remediation target for KI-001 — never ports the prototype's plaintext storage; KI-001 remains open until the control is built, tested, and independently verified.**

- **R-5.1 — MUST** use the approved identity/authentication framework only; **MUST NOT** hand-roll a custom cryptographic authentication or session protocol.
- **R-5.2 — MUST** store passwords with a strong adaptive hash (Argon2id/bcrypt); plaintext or reversible storage is prohibited (implements the designed remediation target for KI-001; the Known Issue remains open until the control is built, tested, and independently verified).
- **R-5.3 — MUST** provide MFA and **step-up** hooks for privileged roles and high-risk actions (payments, period unlock, posting-rule activation, security administration).
- **R-5.4 — MUST** implement rotating refresh tokens with **reuse detection**; a replayed token invalidates the whole token family and raises an alert.
- **R-5.5 — MUST** support server-side **session revocation** and rotate the session on privilege change (session-fixation prevention).
- **R-5.6 — MUST** set auth cookies `Secure` + `HttpOnly` + `SameSite=Strict`, with idle and absolute timeouts.
- **R-5.7 — MUST NOT** place credentials, tokens, or secrets in URLs, logs, or client-accessible storage.
- **R-5.8 — MUST** return **uniform** password-reset and login responses that do not enable account enumeration; reset tokens are single-use, time-limited, high-entropy, out-of-band.

## 6. Authorization and Tenant Isolation

Implements Security Architecture §5–§6; Posting Spec AC-7; mitigates T-04/T-05/T-06/T-07/T-16/T-17/T-27. **Implements the designed remediation target for KI-002; KI-002 remains open until the control is built, tested, and independently verified.**

- **R-6.1 — MUST** enforce **policy-based, server-side** authorization on **every** protected operation, deny-by-default, regardless of UI (implements the designed remediation target for KI-002; the Known Issue remains open until the control is built, tested, and independently verified).
- **R-6.2 — MUST** perform **object-level** authorization (BOLA/IDOR defence): verify the caller may act on the specific resource instance, not just the endpoint.
- **R-6.3 — MUST** scope every read and write by the authenticated `CompanyId` (and `BranchId` for branch-scoped entities), applied server-side and, where available, reinforced by database RLS.
- **R-6.4 — MUST** gate actions on **permission flags**, never on hard-coded role-name strings (matches the existing dynamic-permission pattern, e.g. `pricing.viewCost`, `accounting.rules.admin`).
- **R-6.5 — MUST NOT** rely on hidden or disabled UI controls as an access control; UI visibility is UX only.
- **R-6.6 — MUST** enforce **Separation of Duties** and **Maker/Checker** where specified (payments, period unlock/close, posting-rule lifecycle, user/permission administration, security-configuration changes); the approver **MUST** be distinct from the initiator (SEC-AC-09).
- **R-6.7 — MUST** perform permission checks at the **handler/service** layer (business boundary), not only at the edge.
- **R-6.8 — MUST** separate administrative operations (e.g. `accounting.rules.admin`, user/permission admin) from ordinary operations with distinct permissions and audit.
- **R-6.9 — MUST** have background workers **re-authorize and re-scope** tenant context on each message — workers are untrusted callers (Security Architecture §3; §13 of this document).
- **R-6.10 — MUST** include negative tests for cross-tenant access and IDOR/BOLA on every protected resource (§17; SEC-AC-06/07).

## 7. Accounting and Financial Integrity

Binds directly to the Accounting Posting Service Spec (AI-1…AI-8, AC-1…AC-14). Mitigates T-13/T-14/T-15. **Implements the designed remediation target for KI-008/024 (delete/edit) and KI-009 (duplicate posting); these Known Issues remain open until the controls are built, tested, and independently verified.**

- **R-7.1 — MUST** route **all** legal-ledger writes exclusively through `PostingService`; it is the only writer (AI-1; AC-1). Cross-ref **AC-1**.
- **R-7.2 — MUST NOT** allow any business module to write `JournalEntry`/`JournalLine` (or snapshot/audit/Outbox ledger tables) directly (AI-2). Cross-ref **AC-1/AC-7**.
- **R-7.3 — MUST** keep posted journals **append-only**; `UPDATE`/`DELETE` on a posted entry is rejected at DB and service (AI-3/AI-4). Cross-ref **AC-1**.
- **R-7.4 — MUST** correct by **dated reversal**, never by update or delete; the original is untouched (AI-5; ACC-C). Cross-ref **AC-9**.
- **R-7.5 — MUST** have the **server build** journal lines from the event identity + inputs; the API never accepts final posting lines from callers (Posting Spec governing principle). Cross-ref **AC-7**.
- **R-7.6 — MUST** validate balanced entries (`Σdebit = Σcredit`, ≥2 lines) before persistence, else `ACC_UNBALANCED_ENTRY`. Cross-ref **AC-2**.
- **R-7.7 — MUST** enforce **idempotency** (idempotency key + request hash): identical re-sends return the stored result; a different hash on the same key returns `ACC_IDEMPOTENCY_CONFLICT`. Cross-ref **AC-4**.
- **R-7.8 — MUST** enforce **duplicate prevention** via the unique posting key (e.g. order→invoice, month payroll, invoice payment), else `ACC_DUPLICATE_POSTING` (implements the designed remediation target for KI-009; the Known Issue remains open until built, tested, and independently verified). Cross-ref **AC-5/AC-14**.
- **R-7.9 — MUST** enforce **period-lock** centrally via the single `PeriodLockService`; posting/reversal in a locked period returns `ACC_PERIOD_LOCKED`. Cross-ref **AC-6**.
- **R-7.10 — MUST** use **immutable snapshots** for rates/costs; built lines never reflect later live changes (AI-6). Cross-ref **AC-8**.
- **R-7.11 — MUST** persist journal, journal lines, snapshot, audit record, idempotency record, and Outbox message **atomically in one transaction**; failure at any step rolls back the entire set. Cross-ref **AC-3/AC-10**.
- **R-7.12 — MUST NOT** return a success response before the posting transaction commits (no false success). Cross-ref **AC-11**.
- **R-7.13 — MUST** stamp full traceability on every entry (`SourceType/SourceId/RuleId/RuleVersion/EventDate/CorrelationId`) and reference only active accounts, else `ACC_ACCOUNT_NOT_FOUND`/`ACC_ACCOUNT_INACTIVE`. Cross-ref **AC-12/AC-13**.
- **R-7.14 — MUST NOT** implement soft delete (`IsDeleted` or any hide/void-in-place marker) on `JournalEntries`, `JournalLines`, `PostingSnapshots`, `AuditEvents`, or Outbox ledger records (Posting Spec §13). Cross-ref **AC-1/AC-9**.

## 8. Database Coding Standard

Implements Security Architecture §10; SEC-AC-07/08/14; Posting Spec §3 constraints.

- **R-8.1 — MUST** use parameterised queries / ORM binding **only**.
- **R-8.2 — MUST NOT** build SQL by string concatenation or use untrusted input to construct identifiers, table/column names, or dynamic SQL.
- **R-8.3 — MUST** submit migrations for **separate** review from application code (§18 security-reviewer trigger).
- **R-8.4 — MUST** run the application under a **least-privilege** DB principal: `INSERT`/`SELECT` on ledger tables, **no `UPDATE`/`DELETE`** on posted entries/lines, and **no DDL**.
- **R-8.5 — MUST** enforce integrity in-database: foreign-key, unique, check, and **tenant-isolation** constraints, including composite/cross-company FK rejection (SEC-AC-07) and the Posting Spec constraint set (balance, `Debit XOR Credit`, non-negative, unique posting key, one-reversal-per-original).
- **R-8.6 — MUST** define explicit **transaction boundaries** and use only approved isolation levels.
- **R-8.7 — MUST** handle concurrency with `ROWVERSION` optimistic checks or an approved atomic operation (unique key + idempotency for insert races); no unguarded read-modify-write.
- **R-8.8 — MUST NOT** include nullable columns in a primary key.
- **R-8.9 — MUST NOT** implement soft delete for legal-ledger records (mirrors R-7.14).
- **R-8.10 — MUST** implement RLS policies enforcing the `CompanyId` (and branch) predicate at the database, independent of application filters.
- **R-8.11 — MUST** map database errors to typed application errors; raw DB errors are never surfaced to clients (see §10).
- **R-8.12 — MUST NOT** execute production DDL from the application principal; migration/DDL uses separate, vaulted credentials.

## 9. Cryptography and Secrets

Implements Security Architecture §7 (secrets, encryption at rest) and §14 (backups); SEC-AC-12/20; mitigates T-21/T-24/T-32/T-33/T-34. **Implements the designed remediation target for KI-003 (no XOR/obfuscation); KI-003 remains open until the control is built, tested, and independently verified.**

- **R-9.1 — MUST** use approved, current cryptographic libraries only.
- **R-9.2 — MUST NOT** implement custom cryptography or custom cryptographic protocols.
- **R-9.3 — MUST** store all secrets in the approved vault/secret store.
- **R-9.4 — MUST NOT** place secrets or keys in source, configuration, logs, test fixtures, screenshots, error messages, or JSON payloads (`InputPayload`, `FrozenInputs`, audit `Detail`, Outbox `Payload`).
- **R-9.5 — MUST** use **authenticated encryption** (e.g. AES-GCM) for data at rest and backups; XOR, Base64, or obfuscation as "protection" is prohibited (implements the designed remediation target for KI-003; the Known Issue remains open until the control is built, tested, and independently verified).
- **R-9.6 — MUST** support key identifiers, envelope encryption, and documented **rotation** (scheduled and on-compromise).
- **R-9.7 — MUST** use a cryptographically secure RNG for tokens, keys, nonces, and identifiers; no `System.Random`/`Math.random` for security values.
- **R-9.8 — MUST** distinguish hashing (one-way: passwords, audit chain) from encryption (reversible: field-level confidential data) and apply the correct primitive.
- **R-9.9 — MUST NOT** treat encoding (Base64/hex) or XOR as confidentiality or integrity.
- **R-9.10 — MUST** apply redaction/masking by data classification (Security Architecture §7 matrix) and pass repository **secret-scanning** before merge (§15/§17).

## 10. Logging, Audit, and Error Handling

Implements Security Architecture §12; SEC-AC-17/18; mitigates T-18/T-31/T-32. Distinguishes the three log planes.

- **R-10.1 — MUST** emit **structured** logs with a propagated `X-Correlation-Id` on every line across API, DB context, workers, and Outbox.
- **R-10.2 — MUST NOT** log secrets, credentials, tokens, or unrestricted PII/financial payloads; log by classification (reference/id only for Internal; never for Restricted).
- **R-10.3 — MUST** neutralise **log injection** by encoding/escaping user-influenced values before they enter a log sink.
- **R-10.4 — MUST** keep the three planes distinct: **Security audit** (authN/authZ/privilege/MFA/step-up/Maker-Checker/secret-access/admin), **Operational audit** (business events and pre-transaction rejections, e.g. `PostingRejected`), and the **legal-ledger audit** (`AuditEvents` inside the posting transaction). They are not merged.
- **R-10.5 — MUST** implement the legal-ledger audit as **tamper-evident** (append-only hash chain per `CompanyId`, or approved DB-ledger) with verification and alerting (SEC-AC-17; implements the designed remediation target for KI-004; the Known Issue remains open until the control is built, tested, and independently verified).
- **R-10.6 — MUST** return **typed** public error codes only.
- **R-10.7 — MUST NOT** leak stack traces, SQL, file paths, internal identifiers, or internal object structure to clients; full detail stays server-side (SEC-AC-18).
- **R-10.8 — MUST** fail securely on error (deny/rollback) and **MUST NOT** return success for a write that did not commit (false-success prevention; ties to R-7.12).

## 11. API Coding Standard

Implements Security Architecture §8 and the "Storage→Email / →External Services" boundaries (§3); mitigates T-07/T-25/T-26/T-29/T-30.

- **R-11.1 — MUST** version APIs by URI major version (`/api/v1/...`); breaking changes require a new version with a deprecation window.
- **R-11.2 — MUST** treat the `Idempotency-Key` and `X-Correlation-Id` headers as **authoritative**; the server generates a correlation id when absent.
- **R-11.3 — MUST** apply **rate limiting** per-identity and per-IP on authentication and write endpoints (SEC-AC-19).
- **R-11.4 — MUST** enforce **anti-replay** via idempotency + request-hash, and nonce/timestamp checks on sensitive callbacks.
- **R-11.5 — MUST** apply CSRF defence consistent with the authentication model (cookie-based flows protected; token/`SameSite` as designed).
- **R-11.6 — MUST** enforce a CORS **allow-list**; wildcard origins with credentials are prohibited.
- **R-11.7 — MUST** enforce pagination and query limits; unbounded result sets and unbounded `IN`/filter expansions are rejected.
- **R-11.8 — MUST** allow only **allow-listed** fields for filtering and sorting; no arbitrary client-driven query/column expressions.
- **R-11.9 — MUST** apply request timeouts and honour cancellation tokens on long-running operations.
- **R-11.10 — MUST** return the secure, typed error contract (§10); no internal detail leakage.
- **R-11.11 — MUST** verify **webhook signatures** (and replay nonce, source allow-list) before any state change from an inbound callback.
- **R-11.12 — MUST** allow-list outbound URLs and block internal/metadata ranges to prevent **SSRF**; **MUST NOT** issue outbound calls to user-controlled URLs.

## 12. File and Email Processing

Implements Security Architecture §11; SEC-AC-15/16; mitigates T-09/T-10/T-11/T-12/T-28. Email-ingestion controls are **Planned** — this standard governs them when built.

- **R-12.1 — MUST** land every upload in **quarantine** first; release to the tenant store only after successful validation and scan.
- **R-12.2 — MUST** validate extension, MIME, **magic bytes**, and size against a per-feature allow-list; mismatches are rejected.
- **R-12.3 — MUST** scan every file for malware before it becomes accessible; scan failure ⇒ quarantine, never accept.
- **R-12.4 — MUST** parse untrusted files in **sandboxed** parsers with type/size limits.
- **R-12.5 — MUST NOT** execute macros or embedded code during extraction or parsing.
- **R-12.6 — MUST** extract archives safely with entry-count, total-size, and depth limits to defeat zip bombs and decompression attacks.
- **R-12.7 — MUST** prevent path traversal; resolved paths are constrained to the intended directory.
- **R-12.8 — MUST** use server-**generated** internal filenames/paths; client-supplied names never determine storage location.
- **R-12.9 — MUST** store files **outside the web root**; no direct/enumerable public object paths.
- **R-12.10 — MUST** serve downloads via short-lived, **signed, tenant-scoped** URLs (SEC-AC-16).
- **R-12.11 — MUST** authenticate inbound email senders (SPF/DKIM/DMARC + sender allow-list) and **MUST NOT** auto-trust email content.
- **R-12.12 — MUST NOT** take an automatic business action from an ingested email or attachment where employee confirmation is required.

## 13. Background Workers and Messaging

Implements the "→ Background Workers" boundary (Security Architecture §3) and Posting Spec §11 (Outbox); mitigates T-19/T-20.

- **R-13.1 — MUST** run workers under **least-privilege**, scoped identities with no ambient admin.
- **R-13.2 — MUST** connect to the message broker over authenticated, encrypted transport.
- **R-13.3 — MUST** re-scope tenant context (`CompanyId`/branch) and re-authorize on each message (mirrors R-6.9).
- **R-13.4 — MUST** make consumers **idempotent** (dedup on `MessageUid`) under at-least-once delivery.
- **R-13.5 — MUST** publish integration events via the **Outbox** pattern, only after the ledger transaction commits (Posting Spec §11).
- **R-13.6 — MUST** retry with bounded backoff and route exhausted/poison messages to a quarantine/dead-letter path.
- **R-13.7 — MUST NOT** write the legal ledger directly from a worker; ledger changes go through `PostingService`.
- **R-13.8 — MUST** version message schemas and handle duplicates and out-of-order delivery (per-aggregate ordering; no global total order is assumed).

## 14. Concurrency and Transaction Safety

Implements Posting Spec §9 concurrency policy; SEC-AC/PostAC-14; mitigates T-13/T-15.

- **R-14.1 — MUST** define an explicit transaction boundary around any multi-write financial operation.
- **R-14.2 — MUST NOT** leave partial financial writes; the atomic persistence set commits or rolls back as a whole (ties to R-7.11).
- **R-14.3 — MUST** handle optimistic-concurrency (`ROWVERSION`) conflicts by returning a distinct response for the **client** to decide re-submission; the server does not silently retry changed business state.
- **R-14.4 — MUST NOT** perform silent automatic retries that could double-apply an effect; safe retries require idempotency.
- **R-14.5 — MUST** treat unique constraints (unique posting key, one-reversal-per-original) as the final duplicate defence at the database.
- **R-14.6 — MUST** honour cancellation tokens and define cancellation behaviour for long operations.
- **R-14.7 — MUST** roll back the whole operation if the audit or Outbox write fails (no false success).
- **R-14.8 — MUST** include race-condition tests (concurrent identical postings ⇒ exactly one entry) (§17; PostAC-14).

## 15. Dependency and Supply-Chain Coding Rules

Implements Security Architecture §9; mitigates T-22/T-23.

- **R-15.1 — MUST** restore only from approved, trusted (private/proxying) feeds.
- **R-15.2 — MUST** pin exact dependency versions with lock files; no floating ranges in production builds.
- **R-15.3 — MUST** minimise dependencies; each addition is justified.
- **R-15.4 — MUST** verify package signatures/provenance (NuGet signed-only; npm integrity hashes) before use.
- **R-15.5 — MUST** generate and retain an **SBOM** per build artefact.
- **R-15.6 — MUST** run SCA vulnerability scanning on every build.
- **R-15.7 — MUST NOT** introduce an abandoned/unmaintained package without a documented risk acceptance (§21).
- **R-15.8 — MUST** review transitive dependencies, not just direct ones.
- **R-15.9 — MUST** run licence checks at the dependency approval gate.
- **R-15.10 — MUST** block release on any **critical** dependency vulnerability.

## 16. Configuration and Environment Security

Implements Security Architecture §2 (secure defaults), §7 (secrets), §8 (headers), §11–§14.

- **R-16.10 — MUST** synchronise clocks (NTP) across services for correlation, tokens, nonce/timestamp checks, and audit ordering.

## 18. Code Review Checklist

Every pull request **MUST** be reviewed against all items below.

1. Architecture conformance (reading order followed; no invented logic).
2. Authorization (server-side, deny-by-default, permission flags — not role strings).
3. Tenant isolation (`CompanyId`/branch scoping; cross-tenant negatives present).
4. Input validation (DTO allow-list, canonicalisation, payload limits).
5. Financial invariants (PostingService-only, append-only, reversal, balance, idempotency, period lock, snapshot).
6. Transaction safety (atomic set; no partial writes; no false success).
7. Concurrency (optimistic checks; no silent retry; unique-key defence).
8. Secrets (none in source/config/logs/fixtures/payloads).
9. Logging (structured, correlation id, no secrets/PII, log-injection-safe).
10. Dependencies (pinned, signed, SCA clean, SBOM).
11. Tests (unit/integration/DB/authz/tenant/concurrency/security-regression present and mapped).
12. Migrations (reviewed separately; least-privilege; constraints present).
13. Error handling (typed public errors; no internal leakage).
14. File/integration risks (quarantine, magic-byte, signed URLs, webhook signatures, SSRF allow-list).

**A dedicated security reviewer is REQUIRED** for changes touching: authentication · authorization · payments · posting · period lock · posting-rule activation · file/email ingestion · encryption · secrets · CI/CD.

## 21. Exceptions and Risk Acceptance

Any deviation from a `MUST`/`MUST NOT` rule requires a recorded exception. No permanent, undocumented exception is permitted.

An exception record **MUST** contain:

- **Exception request** — the specific rule ID being deviated from.
- **Business justification** — why the deviation is needed.
- **Affected control** — the security control and threat/AC weakened.
- **Compensating control** — the interim mitigation in place.
- **Owner** — the accountable individual.
- **Approval** — the **Security Architect** (and acceptance authority per the Threat Model residual register, e.g. CISO for high-risk).
- **Expiry date** — a hard review/expiry, not open-ended.
- **Review requirement** — re-evaluation at expiry; the exception lapses if not renewed.

- **R-21.1 — MUST** record every deviation as above before merge.
- **R-21.2 — MUST NOT** carry a permanent or undocumented exception.
